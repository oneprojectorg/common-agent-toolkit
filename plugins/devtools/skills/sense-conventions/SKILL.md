## `@op/ui` is gone — the design system is `@op/sense`

`packages/ui` was deleted in PR #1790, after the app-wide migration (#1662, #1727, #1738, #1740, #1741) and the Storybook/docs handover (#1782). **There is no `@op/ui`.** An `import { Button } from '@op/ui/Button'` does not resolve, and the React-Aria-era API it exposed (`isDisabled`, `onPress`, `<Modal>`, `<Menu>` / `<MenuList>`, `<Surface>`) is gone with it — Base UI uses the native DOM prop names.

`@op/sense` (`packages/sense`) is **shadcn/ui in its Base UI style**, themed by `@op/styles`. Two halves with different rules:

- **Primitives** — `src/components/ui/<name>.tsx`, generated by `shadcn add`, **regenerable**. Treat as output.
- **Composites** — `src/components/<PascalName>/index.tsx`, hand-written and ours forever.

**Read `packages/sense/CLAUDE.md` before building UI** — it is the authoritative recipe and this skill defers to it on anything it covers in more detail.

### The basics you'll get wrong otherwise

- **Import per component**: `import { Button } from '@op/sense/Button'`. There is no barrel export; `package.json#exports` is the full public list.
- **Get `cn` from `@op/sense/lib/utils`**, never stock `twMerge`. Ours registers the custom type tokens with `tailwind-merge`; the stock one silently drops `text-title` / `font-strong` whenever a `className` merges a colour in.
- **Prefer a sense component over a raw element** — `Button` over `<button>`, `Header1` over `<h1>`, `Field` over a hand-rolled label. Browse with `pnpm w:sense dev` (Storybook, http://localhost:3600).
- **Logical properties only** — `ms-`/`me-`, `ps-`/`pe-`, `start-`/`end-`, `text-start`/`text-end`. Never `ml-`/`pl-`/`left-`/`text-left`. The app ships Arabic, and PRs #1745 / #1751 were the sweep that made RTL correct; don't reintroduce physical properties. Directional icons flip with `rtl:-scale-x-100`.
- **Sense is i18n-agnostic.** Components take copy as props with English defaults and never call `t()`; the app passes translated strings in.

## Colours and the type scale — semantic classes only

- **Colours: semantic classes.** `bg-primary`, `text-muted-foreground`, `border-input`, `bg-muted`, `bg-background`. Raw values live in `packages/styles/tokens.css`, semantic names in `packages/styles/theme.css` (the package entry).
- **Never a raw palette value.** `bg-gray-100`, `text-slate-500` and `bg-white` are all the same mistake: a fixed value doesn't participate in theming, so the element diverges from the surface around it. PR #1795 caught `bg-white` on a new `loading.tsx` shell — "does not participate in theme or token-driven color changes and can visually diverge from the surrounding application." A loading shell is not exempt; it sits next to real content.
- **Never a hex literal.** `bg-[#333]`, `text-[#abc]`.
- **Type scale: `text-label` / `text-title` / `text-headline` / `text-display`.** Defined in `theme.css`, responsive at the `md` breakpoint. These four are the **serif heading** styles — popover and small-card titles, dialog / sheet / card titles. They are not the control-label scale, and swapping a sans label onto one changes the font.
- **`text-xs` / `text-sm` / `text-base` are part of the system — keep using them for control labels and body copy.** `theme.css` says so in two places: the serif tokens are "NOT sans control labels, which use the generic scale (`text-base` etc., tracking 0)", and the Figma modes' "xs/sm/base … match the scale above". PR #1892 is the thread to cite: Greptile flagged `text-sm` / `text-base` in a new assignment sheet as bypassing the type scale, the review answered *"text-sm is ok to use as noted in the Sense theme.css which notes that those default tokens are left as is to use"*, and the bot withdrew the finding. **Don't rewrite a `text-sm` label into `text-label` to satisfy a bot** — rebut with the `theme.css` comment, per the rebuttal rule in `code-conventions`.
- **`text-lg` / `text-xl` / `text-2xl` are the ones with no Figma equivalent.** `theme.css` keeps them at Tailwind's defaults "for stock shadcn internals," so in app code reach for `text-title` / `text-headline` / `text-display` instead of climbing the stock scale.
- **`bg-white` and the raw grays are still the highest-recurrence flag on new UI.** `bg-white` was caught on three separate surfaces in four days — a reviews `loading.tsx` shell (#1843), the new assignment dialog and panel (#1848), and a proposal search field's notice (#1852). None were arbitrary values; all were the default thing to type. Grep your own diff for `bg-white`, `text-gray-`, `bg-gray-` before pushing — it costs one command and it is what the bot will run.
- **`text-title-*` is the retired pre-sense scale** (`text-title-lg`, `text-title-base`, `text-title-sm14`) — PR #1754 retired it and #1791 dropped the rest of the pre-sense token layer. Never write one in new code.

### Why three pre-sense heading tokens still exist (and why that isn't permission)

`theme.css` deliberately keeps `--text-title-lg` / `--text-title-base` / `--text-title-sm14` for exactly one consumer: `headingClasses` in `@op/styles/constants.ts`. Those class strings are baked into server-rendered HTML by `@op/common`'s `StyledHeading` extension, and that HTML is the source text hashed into `content_translations.contentHash`. Changing the strings invalidates every cached translation of every decision and proposal body in every locale — paid re-translation plus orphaned rows — and restyles already-published content. Proposals can also be stored as raw HTML, so the class names sit in rows no grep can see.

Moving `headingClasses` onto the sense scale is its own task with a design decision and a cache-purge call. **Until then these stay and nothing new references them.** The comment block in `theme.css` says so; don't read the surviving tokens as an escape hatch.

The `--op-*` palette and `shared-styles.css` are gone entirely (#1753, #1756, #1791) — `primary-teal`, `neutral-gray1`, `neutral-black` are not classes any more.

## Stay on the scale — no arbitrary values, anywhere

Reach for the named Tailwind scale (`max-w-96`, `gap-4`, `p-6`) before an arbitrary value. This is the most-flagged convention in the repo, and three separate reviews in one fortnight landed on it:

- **It's every utility, not just sizing.** `stroke-[1.5]` got flagged twice (#1673, #1726) because Tailwind ships only `stroke-0` / `stroke-1` / `stroke-2`: "bypassing the repository's Tailwind token convention and making icon styling harder to maintain consistently." Snap to an existing tier — or, if the off-scale value is genuinely load-bearing (an app-wide icon stroke), add a CSS token (`--stroke-icon`) and reference it (`stroke-[var(--stroke-icon)]`) so there's one place to change it.
- **A repeated arbitrary value is a missing token.** PR #1796 added a responsive dialog height as an arbitrary value "and the same pattern is repeated across the updated call sites … preventing centralized updates through the design system." Once you've written the same bracket value twice, you've defined a token by hand — put it in `theme.css` instead.
- **Stories and fixtures are not exempt.** PR #1797 flagged `w-[36rem]` in a `*.stories.tsx`. The story is the worked example the next contributor copies; an arbitrary value there propagates.

If a design genuinely needs an off-scale value, add a token in `packages/styles/tokens.css` and a semantic name in `theme.css` rather than sprinkling brackets.

## Tailwind v4 traps

**A bare number in a typed utility silently produces nothing.** Tailwind v4 resolves `duration-*` through `--value(--duration-*, [time])`: it looks for `--duration-<n>` in the `@theme`, and failing that tries to parse the bare value as a CSS `[time]`. A unitless integer is not a valid time, so **`duration-450` matches nothing, generates no CSS, and is dropped at build with no warning** — the transition runs instantly. Use the bracket form with an explicit unit: `duration-[450ms]`.

PR #1688 shipped this on both a drawer overlay and a popup. The failure is invisible in code review *and* in a typecheck — the only tell is that the animation doesn't animate. The same trap applies to any theme-keyed utility given an off-theme bare value; when a visual change is the whole point of the PR, open the page and confirm the CSS actually landed.

**Delete conflicting utilities from a base class string.** `tailwind-merge` silently discards the loser when two utilities in the same group collide (`cursor-default` alongside `cursor-pointer`), so the dead class has no runtime effect but reads as intentional to the next contributor. PR #1671.

**A child cannot un-dim an opacity-dimmed ancestor.** CSS `opacity` composites the entire parent render-buffer before display, so `opacity-100` on a child of an `opacity-50` wrapper is a no-op. To keep one element bright inside a muted block, dim the siblings with colour tokens (`text-muted-foreground`) instead of putting an opacity layer on the shared wrapper. PR #1675.

## Accessibility and semantics

Base UI gives you focus management, roving tabindex, typeahead, `aria-expanded` / `aria-controls` / `aria-selected` wiring, dismissal and scroll locking. **Don't reimplement or work around any of it.** These are the parts it can't infer.

### The four obligations

1. **Name every icon-only control.** `<Button size="icon-sm"><LuX /></Button>` is a nameless button — add `aria-label={t('Close')}`. The single most common defect in this codebase.
2. **Label every input.** `Field` + `FieldLabel`, or `htmlFor` matching the control's `id`. A placeholder is not a label.
3. **Announce content that changes without a navigation.** Async results, live counts, validation errors, save states → `aria-live="polite"` on the region that updates.
4. **Keep clickable things focusable and semantic.** Never `onClick` on a `div`. If a whole surface must be clickable, use `Button variant="bare"`, which keeps button semantics without imposing button styling.

Anything that animates needs a `motion-reduce:` branch.

### The rules reviewers keep catching

- **`aria-label` REPLACES the visible text — never use it to bolt on extra information.** A screen-reader user gets only the label, so `aria-label={reviewerNames}` on a trigger whose visible text reads "3 Reviewed" announces "Alice, Bob" with no hint of what the control is. To *add* detail, let the tooltip / popover content be the accessible description, or wire `aria-describedby` — both get through. PR #1711.
- **`aria-label` describes the ACTION, not the display label.** `aria-label="Profile photo"` on an upload button leaves the user unable to tell what it does. Prefer `Upload ${label}`. PR #1626.
- **`pointer-events-none` is not `disabled`.** It blocks mouse and touch but not Tab-then-Space/Enter, and `aria-busy` is purely informational — so a "loading" button styled that way is still keyboard-activatable and double-fires for any caller that doesn't separately guard on `isPending`. Set the native `disabled` so the browser's own not-actionable semantics apply. Sense's `Button` does exactly this (`loading` adds `pointer-events-none` *on top of* `disabled`, with `disabled:opacity-80` so the spinner stays readable). Keep `pointer-events-none` alone only for the link-rendered case, since an anchor ignores `disabled`. PR #1670.
- **An inert item must not be keyboard-reachable.** Interactive-list primitives (menu items, command items, rows) are focusable and Enter-activatable by default; if the handler early-returns for some subset, the user lands on it, presses Enter, and gets silence. Pass `disabled` for that subset so keyboard navigation skips it. PR #1669.
- **Don't render an affordance the component can't honor.** A `showDragHandle` defaulting to `true` renders a real button with `aria-label="Drag to reorder"` even when no `dragHandleProps` were passed. Default the affordance **off**, or derive it from the props that make it work (`Boolean(dragHandleProps)`), so the safe path is the default path. PR #1659.
- **A stateful control's visible label must track its state.** `{isSelected ? t('Advancing') : t('Advance')}`. PR #1711 caught the label frozen at "Advance" after a Toggle migration — "making it impossible for sighted users to tell whether a proposal is advancing."
- **Sortable column headers need `aria-sort`.** An arrow icon leaves screen-reader users with no way to know which column is sorted or how. Set `"ascending"` / `"descending"` / `"none"` on the `<th>` from the `active` flag and direction you already use for the arrow. PR #1702.
- **Only render an `<a>` when a real `href` is present; render a `<div>` otherwise.** An href-less anchor still carrying `target="_blank"` is semantically ambiguous and may be announced as an unlabelled link. PR #1626.
- **Default `dir` to `"auto"` on text-bearing components** (`dir = 'auto'` as a param default) so RTL content resolves its own writing direction. Keep it consistent across siblings in a file — sense's `Header1`–`Header4` and `GradientHeader` all do. PR #1622.
- **`role="tabpanel"` only when an associated tab element actually exists**, paired with `aria-labelledby` pointing at it. Applying the role unconditionally in a single-pane layout leaves the panel with no accessible name. PR #1622.
- **A standalone line of text is a `<p>`, not a `<span>`.** A screen reader treats a paragraph as a navigable block and gives it its own boundary; an inline `<span>` runs into whatever sits beside it. PR #1943 (nourmalaeb) on `ReviewResultCard`: *"We should use a `<p>` instead of a `<span>` here for better screen-reader support."* Reach for `<span>` only when the text really is inline inside a larger sentence.
- **Links in prose must be underlined, not colour-only** — colour alone fails the axe `link-in-text-block` rule. PR #1524.

Check your work in the **A11y** panel of the component's story (`pnpm w:sense dev`) — axe runs live against what's on screen. It is not CI-enforced yet (the headless gate is blocked upstream; see `packages/sense/README.md`), so reading it is a manual step you owe. Routes are covered by `pnpm a11y:baseline` — see the `test-conventions` skill for the known-violations ledger.

## Base UI behaviours that bite

Each of these cost real debugging time (see `packages/sense/CLAUDE.md` for the full list):

- **Guard `data-*` variants with an explicit `=true`.** Base UI and cmdk stamp `data-selected="false"` as well as `"true"`, and a bare `data-selected:` matches *both*. Always write `data-[selected=true]:`. Symptom: every item in a list renders as selected.
- **`Select.Value` renders the raw value, not the label.** A `<Select>` with `value="en"` displays `en`, not `English`. Pass the value→label map to the root's `items` prop, or keep `value === label`.
- **Native DOM prop names**: `disabled`, `onClick`, `checked`, `loading` — not React Aria's `isDisabled` / `onPress` / `isSelected`.
- **There is no `ButtonLink`** — render an anchor through the button: `<Button render={<Link href="/next" />} variant="link">`.
- **Menu labels must sit inside a `*MenuGroup`** or Base UI throws error #31; menus need an explicit `*Content` wrapper and `*Trigger asChild`.
- **Cancel a built-in handler with `event.preventBaseUIHandler()`**, not `stopPropagation`.
- **`SkeletonText` defaults to `lines={3}`.** Set it to match the real content rather than copying a number from elsewhere (see `component-file-structure` on counting the bars).

## Reach for the existing component before writing a new one

Check `packages/sense/package.json#exports` first — it is the complete public list, and it is long. The recurring review-rejection shape is "we have a `<Y>` for this — use that."

| You think you need… | Reach for |
|---|---|
| A loading placeholder | `Skeleton` / `SkeletonText` |
| A rich text editor with the Common toolbar | `RichTextEditor` |
| A heading | `Header1` … `Header4`, `GradientHeader` |
| An empty state | `Empty` |
| A modal | `Dialog` (or `Drawer` / `Sheet` for the mobile surface) |
| A page-level "you can't see this" / "this isn't here" screen | `apps/app/src/components/screens/` (`ForbiddenScreen`, `PageError`, `PageNotFound`) |

**Use the same primitive on both halves of one feature.** A PR that reaches for `@op/sense/ScrollArea` in its dialog and a raw `overflow-auto` div in the panel beside it ships two scroll behaviours, two scrollbar treatments and one of them outside the design system — and the diff reads as fine because each is locally reasonable. PR #1848. When you add the second scrollable / truncating / empty region in a feature, look at what the first one used.

When the existing component is *close* but not quite right, extend it (add a variant or a prop) rather than forking. The threshold to extract a variant is the second time you'd otherwise duplicate the override — until then, use the existing variant once and leave a comment saying why.

**A presentational piece a second surface will want belongs in `@op/sense`, and the reviewer will say so.** PR #1966 on a list row built inside `ReviewAssignmentsList.tsx`: *"Would love to have this in op/sense."* When the thing you are building is generic markup with no feature knowledge in it, expect that ask — answer it with a follow-up PR that moves it (scope discipline still applies; don't grow the feature diff into a package change), and say in the body that you're deferring it.

**A net-new design-system component needs a design decision behind it — composition doesn't.** PR #1775 (`CurrencyField`) was closed for exactly this: *"CurrencyField would add net-new @op/ui surface without design approval. Decision: the reviewer money input reuses the existing pattern (NumberField + currency-symbol `prefixText`, as `CollaborativeBudgetField` does) — the currency is template-locked so the input is just a number."* Before proposing a new primitive, find the surface in the app that already solves the same problem by composing two existing ones, and copy that. If the composition genuinely can't express it, that's a design conversation, not a PR.

When you must open an external link programmatically, always pass the features string: `window.open(url, '_blank', 'noopener,noreferrer')` — the missing opener reference prevents reverse-tabnabbing. PR #1522.

## Adding to `@op/sense`

The full recipes are in `packages/sense/CLAUDE.md`. The parts that get missed:

- **Run `shadcn add` from the package only** (`pnpm w:sense dlx shadcn@latest add <name>`) — the app has no `components.json` by design.
- **Add the `package.json#exports` entry**, alphabetised. Skipping it gives `Cannot find module '@op/sense/<Name>'`; that error is the drift signal, not something to work around.
- **Rewrite the CLI's `@/lib/utils` imports to relative paths.** Composites import primitives relatively (`../ui/button`), not through the public subpath — internal restructuring shouldn't touch the public API. Stories are the exception; they import through the subpath so they document what a consumer writes.
- **Do not restyle a generated primitive to use OP tokens.** It should use only shadcn's semantic classes, which already resolve to OP values through `theme.css`. If it looks wrong, fix the mapping in `theme.css`, not the component — editing a primitive's colours makes it unregenerable.
- **The story is part of the change**, not a follow-up. A component with no story is undocumented. Composites get JSDoc as their API documentation; primitives get JSDoc only on *our* deviations, since regeneration deletes the rest.
- **Delete `rtl:space-x-reverse`** if the CLI emits it — Tailwind v4 already emits `margin-inline-end`, and the v3 holdover *introduces* a bug here.

### Keep the package framework- and i18n-agnostic

- **`packages/sense` must not depend on `next`** — never import `next/image` or any `next/*` inside a sense component. When a component needs an optimized image, take a render/slot prop and let the **app** inject `next/image`. PR #1480 (`BannerImageField` → `renderPreview`); `AvatarUploader` uses a plain `<img>` for the same reason. Wrinkle: `next/image` can't optimize a transient `blob:` optimistic URL, so the internal fallback renders a plain `<img>` for the blob frame.
- **Same rule for i18n.** A package component can't call the app's translation hook, so it accepts all user-facing copy from the caller — grouped into a single `copy` prop object rather than sprayed across six string props. PR #1626.
- **Never add `@op/sense` as a runtime dependency of anything inside the package** — it's a leaf.

## Labels, headings and images

- **Sentence case, matched to siblings.** "Add to organization", not "Add to Organization". A lone title-cased entry in a block reads as a visual inconsistency. Apply the correction across **every** locale dictionary, not just `en.json`. PR #1649.
- **Semantic hierarchy: the page's main title is the `h1`.** The hero title is the semantic `<h1>`; a secondary top-bar title is an `<h2>`. PR #1482.
- **An empty-string fallback for a display value renders visibly broken copy.** `phase.name ?? ''` produced a tab reading "Reviews from " — fall back to an identifier (`?? phase.phaseId`) so the degraded case is diagnosable rather than mysterious. PR #1701.
- **`next/image` in a CSS-sized container uses `fill` + `object-cover`**, not fixed `width` / `height`. Fixed intrinsic dimensions pin the requested asset to one size, so a `width={48}` avatar in a `size-8` container over-fetches, and without `object-cover` a non-square source crops badly. PR #1670.
- **An absent image URL is `?? undefined`, not `?? ''`.** An empty string is a non-null `string`, so it satisfies the type while meaning "no URL" — it only works because the consumer happens to falsy-check.

## Verify

```bash
pnpm typecheck        # whole repo
pnpm w:sense build    # every story has to compile and bundle
pnpm format
```

`pnpm w:sense build` / `dev` call Storybook directly, so on a fresh clone run `pnpm build` once first — `@op/styles` resolves to a generated `dist/styles.css`, and without it you get `Failed to resolve entry for package "@op/styles"`. CI runs `turbo build --filter=@op/sense`, which compiles the dependency first (#1782 / #1784).
